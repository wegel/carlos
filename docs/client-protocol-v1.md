# Carlos client protocol version 1 (provisional)

The `carlos-proto` crate defines shared JSON data without sockets, clocks or terminal dependencies. EP018 introduced numbered core facts. EP018a adds bounded live tool output and documents the missing terminal commands in `docs/terminal-client-migration.md`. EP019a exercises these types with real local headless clients; EP019b switches the terminal after owner review and workflow parity. Version 1 remains provisional until those consumers prove its coverage; there are no deployed clients requiring compatibility shims. EP020 adds network access and device tokens. Schema output and language bindings wait for a concrete consumer.

## Envelopes and addresses

Every request carries `jsonrpc: "2.0"`, an `id`, a `method` and an object `params`. The id is a string or signed 64-bit integer; null and fractional request ids are invalid. Responses contain the same id and either `result` or `error`, never both. A failure to parse an envelope may return a null id. Notifications contain `jsonrpc`, `method` and `params` with no id. The Rust types are `Request`, `Success<T>`, `Failure` and `NotificationMessage`.

For example, a client greets a server with:

    {"jsonrpc":"2.0","id":"hello-1","method":"hello","params":{"protocol":1,"client":"carlos-headless"}}

The network server will check the token and call `check_protocol` before accepting commands or subscriptions. EP019a's Unix listener uses the private path and OS-user boundary; EP020 implements device-token authentication. The carlosd executable serves the local command set; docs/daemon-protocol.md records its budgets and recovery rules. Version 1 is the only accepted version. A mismatch returns Carlos error `-32001`. Standard JSON-RPC errors remain `-32700` for malformed JSON, `-32600` for an invalid envelope, `-32601` for an unknown method and `-32602` for invalid parameters. The daemon returns explicit Carlos errors for unknown sessions, retired entries, unavailable choices and answers to already resolved cards. Failed commands do not allocate entry ids or advance the session cursor merely because a client attempted them.

A session address contains 32 lowercase hexadecimal characters. An entry or approval address contains 32 lowercase hexadecimal characters, a hyphen, then 16 lowercase hexadecimal characters. Clients treat the whole string as opaque. They must not derive order, backend identity or row position from it. The parser rejects uppercase, short ids and non-ASCII characters. A syntactically valid id does not prove that the core ever issued it. A lookup must still find the live row or card. Native thread ids and backend request ids remain inside the core; ordinary user or backend prose can still mention an id as text.

A cursor (`seq`) is a canonical decimal **string**, including zero as `"0"`. Decimal strings preserve all 64 bits in JavaScript. Leading zeros, signs, numeric JSON values and values above `18446744073709551615` are invalid. Each session starts before event 1; the core advances its clock without wrapping. A native fork, history reload or transcript clear preserves the logical session address and clock while retiring the affected entry addresses.

## Client commands

All names and parameter keys are case-sensitive. Optional fields may be absent or null. Fields that the core knows to be absent are encoded as null, so a full replacement can clear old facts. An empty parameter list is encoded as `{}`.

- `hello`: `protocol` (integer), `client` (string), optional `token` (string, empty for the private Unix listener), optional `resume` (ClientId), `resume_token` (private ResumeToken) and `instance` (DaemonId). Returns `HelloResult` with `protocol`, `host`, `daemon_version`, `instance`, `client`, `resumed`, nullable `next_operation` and private `resume_token`. A new daemon lifetime gets a fresh instance id.
- `sessions/watch`: `{}`. Returns `Sessions` with `sessions`, then receives `sessions/changed` notifications.
- `session/create`: `operation`, `backend` (`codex`, `claude`, `grok`), absolute `cwd` (string), `name` (optional string). Returns `OperationResult` with the reserved logical session id. A lost reply retries that same create without launching another backend. Native startup and a durable native address must both succeed before the result becomes accepted.
- `session/subscribe`: `session`, optional `since` cursor. Returns `SubscribeResult`, either `kind: "snapshot"` with `snapshot`, or `kind: "replay"` with `events` and final `seq`. The server must establish this cursor before delivering later notifications for the subscription.
- `session/unsubscribe`: `session`. Returns null.
- `session/history`: `session`, `before` (live entry id), `limit` (clamped to 1 through 1000). Returns `History` with `entries`, `has_older`, `seq`. Rows precede `before` strictly, in chronological order. A retired or foreign cursor fails; the server never guesses a replacement position.
- `session/send`: `session`, `text`, `operation` (ClientOperation), `policy` (`steer`, the default, or `queue`). Returns an OperationResult describing admission, then private `operation/updated` notifications describe native acceptance/failure. The accepted user entry carries the same operation. The core maps its private UUID echo token to the originating operation; Codex returns that token as userMessage.clientId, Claude uses the submitted prompt UUID, and Grok binds its owner-created echo directly. No echo or editor decision uses text equality.
- `session/rename`: `session`, `operation`, `name` (at most 4096 UTF-8 bytes). Returns a private OperationResult; an accepted name appears in shared SessionInfo. Unsupported backends and control characters fail before native dispatch. Repeating a retained operation does not rename twice.
- `session/rewind`: `session`, `operation`, selected stable prompt `entry`, edited `text` (at most 512 KiB). The owner resolves the native anchor and validates it before forking. Fork and edited send remain one operation across follow-up calls; Claude waits for its exact asynchronous acknowledgement. Failed/retired targets return only the submitting client's text. A lost reply never authorizes a second fork or resend.
- `session/interrupt`: `session`, `operation`, `turn` (opaque TurnId). Returns OperationResult. The owner checks the exact current turn before dispatch; backend facts describe what actually stopped. A successful request does not assert that the backend finished.
- `session/approve`: `session`, `approval` (live card id), `operation`, `answer`. An answer is either `{"kind":"decision","decision":"once"}` or `{"kind":"input","value":...}`. Other decisions are `session`, `deny`, `cancel`. Returns OperationResult. The handler checks the live card, offered choices and submitted state; structured values pass the card's question/form checks before native dispatch. One answer wins across clients.
- `session/setRalph`: `session`, `operation`, `on` (boolean). Returns OperationResult. The core may defer a toggle until the current turn ends; the shared event reports accepted state.
- `operation/read`: `operation`. Returns the retained OperationResult for that registered client identity, including pending work. An expired result fails explicitly and never re-executes the command.
- `entry/output`: `session`, `entry`, nullable `cursor`, nullable `limit` (source bytes, default 65536). Returns `OutputChunk`, described below.
- `entry/output/subscribe`: `session`, `entry`, nullable `cursor`. Returns the first `OutputChunk`, then receives `entry/output` notifications. Repeating the command replaces that connection's watch for this entry. It does not create another session-event sequence.
- `entry/output/unsubscribe`: `session`, `entry`. Returns null and stops future chunks for that connection and entry. Other clients keep their watches.
- `entry/source`: `session`, `entry`, nullable `cursor`, optional `limit` (clamped to 4 through 65536 source bytes). Returns `SourceChunk` with original UTF-8 `text`, exact byte `offset`, `source {revision,bytes}`, `from`, `next`, `has_more`, `done` and sealed `seq`. It reads any live row, preserves terminal controls exactly, and never reconstructs original text from normalized output. Byte offsets/lengths use canonical decimal strings with all 64 bits preserved, distinct from event cursors.
- `entry/source/seek`: `session`, `entry`, expected body `revision`, decimal-string `offset`, optional bounded `limit`. It returns the same chunk directly at that position, rounding down at most three bytes to a UTF-8 boundary. Old revisions and positions past the body fail. Clients use the returned cursor for continuation; jumping in a large body never requires replaying its prefix.
- `entry/source/subscribe` and `entry/source/unsubscribe`: the same entry/cursor choices as output watches, with `entry/source` notifications and `entry/source/reset` on a lost watch. Source and normalized watches have independent format-bound cursors and share one combined per-peer watch limit. A token from the other format fails.

A plain row above 4096 source bytes has empty inline `text` and explicit `source {revision,bytes}`. Clients fetch that body through bounded source reads; empty inline text must not be displayed as a complete empty body. `source_changed {entry,source}` announces later large-body appends without bulk text in the shared stream. Tool bodies retain their existing separate output facts and can also be fetched as original source. Replacing any body invalidates old source cursors. Snapshot/history pages may contain fewer rows than requested to fit the byte budget; `has_older` and the first stable entry id allow continued history reads.

The serializable command types describe the client boundary. They do not expose Codex JSON-RPC methods, Claude callback ids or terminal key names. The session owner reuses the same native handlers as the embedded terminal.

For a `fields` input, the submitted `value` is an object with a `fields` array. Each answer has `key`, `values` (an array of the listed typed option values) and nullable `text` (free text or notes). Unknown or duplicate keys fail. A field with `multiple: false` accepts at most one listed value. Nonempty text requires `other: true`; `notes_only: true` requires a listed value alongside those notes. A required field cannot be empty. The core checks these rules before converting to a native backend answer. For a `form` input, `value` is the JSON value described by its schema, checked before a native reply. A browser input uses the explicit `once` decision. An unsupported input can be declined or cancelled, but cannot accept an invented empty answer. The owner checks these answers before writing; the embedded terminal keeps its existing local editors until EP019b.

## Submitted text and client editors

EP018a defines `ClientOperation {client,id}`, `SubmittedText {operation,text}` and typed `SubmissionOutcome` facts in carlos-proto. ClientId is an opaque 32-character lowercase hex string. OperationId is a nonzero increasing 64-bit counter encoded as a canonical decimal string; it rejects numbers, zero, signs, leading zeros and overflow. The core carries these ids with accepted queue/fork text and returns them when a command fails or advances. It never receives the current composer or confirmation token. An optional origin remains only for automatic work and legacy in-process test helpers; The daemon requires and authenticates the origin of human commands, deduplicates retries and retains private outcomes for their originating client identity, including after reconnect.

A client applies recovery only for an operation it owns. It restores text into an empty composer, keeps identical text once, or retains the failed submission beside newer typing. Another client's recovery cannot clear or populate its editor. EP018a's recovered-text notices omit F5 instructions; other legacy notices and report consumers still contain terminal policy. EP019b must finish that cleanup so each client supplies its own recovery controls. Labeling a recovered prompt does not imply the backend definitely rejected a timed-out request; The owner preserves each adapter's uncertain-send rule.

## EP019a identity and result contract

The Rust types and golden data now define the identifiers, greeting, operation query and private result variants below. The local daemon implements these handlers and the retained-result store, with process tests for all three adapters. EP019b adds the remaining typed terminal families rather than treating the basic list as complete.

The Unix greeting returns a fresh daemon-instance id and a server-issued ClientId. A reconnect may resume a retained client identity only with its matching private resume token and daemon instance. ClientId is visible in shared rows and is not a credential. The token contains 64 lowercase hex characters, is returned only in that client's greeting and never appears in shared facts. A wrong token for a retained identity fails explicitly. A reconnect with an expired/unknown identity gets a fresh identity; an unknown or expired identity receives a fresh identity and cannot claim old retry rights. A daemon restart keeps saved logical session ids but changes its instance id. Clients then discard old event/retry cursors, obtain fresh snapshots and ask the user how to recover uncertain work. They never automatically resend a possibly written prompt or answer.

Use ClientOperation as the one semantic command identity and the user-entry echo reference. The old client_message_id field has been removed from send/entry data. Keep ClientId opaque. OperationId is a per-client increasing canonical decimal counter encoded losslessly as a string, with checked exhaustion. A JSON-RPC request id still pairs an envelope with its response; it is not a retry identity. Bind human operations to the connection's registered client and reject forged owners; reserve absent origins for automatic work and legacy in-process test helpers.

The daemon keeps bounded pending/recent private outcomes and an admission high-water mark for each retained client. A retry with the same id and payload attaches to pending work or returns the saved result without executing again. The same id with a different payload fails. An older id whose result expired fails as outcome-expired/uncertain and never starts new work. Bound inactive identities as well as their results. An expired identity or new daemon instance cannot promise recovery of an in-memory result. When a client's counter reaches its maximum, next_operation is null; reads/recovery remain possible but a fresh identity is needed for new commands. docs/daemon-protocol.md defines the exact count/byte limits and expiry behavior.

The typed private operation/updated notification and operation/read command recover results after a connection disappears; a disconnected socket cannot consume and lose the only copy. Publish shared conversation/card/session facts through the numbered event stream, send private results only to the owning client identity, and keep editor behavior on the device. Reject ordinary work explicitly before dispatch when its admission queue is full. Hold accepted ordinary commands in arrival order above the core's Busy guard while independently checking priority interrupts and answers. Never interpret a timeout as proof that the backend rejected a write.

OperationResult contains operation, session and state. State.kind is pending, queued, accepted (nullable entry), rejected (message and nullable submitted-text recovery), or uncertain (message and nullable recovery). Accepted describes native command admission, not model/turn completion. Clients display shared turn facts separately. An uncertain result never authorizes an automatic resend. EP019a's owner publishes private results without consuming them when a socket disconnects.

## Session facts

`SessionInfo` contains `id`, nullable `name`, `backend`, nullable `model`, `host`, nullable `cwd`, `phase`, `availability`, nullable `current_turn`, `ralph`, nullable `turn_started_at`, nullable `context` and nullable `quota`.

The core takes the actual backend from the launch caller. It does not guess from compatibility controls, which can be enabled together. The in-process terminal uses host `local`; the daemon will supply its host label. The core reports phase `approval` when an active approval card exists, otherwise `running` when a turn is active, otherwise `idle`. Availability is `dormant`, `restoring`, `starting`, `ready`, `closed` or `unavailable`; a saved session can remain listed while its backend is absent. current_turn is an opaque TurnId that changes with the active native turn and becomes null when idle. An interrupt must name that exact live token, never a native turn id. A queued Ralph toggle does not change `ralph` until the core applies it.

`turn_started_at` is the core's observed start time in Unix seconds, or null when unknown or idle. Clients update their own elapsed timers. A same-thread history read must not restart that timer. `context` contains `used` and `max` token counts last reported by the backend. A missing report stays null. `quota` contains `remaining_pct` and nullable `resets_at` in Unix seconds. Clients compute days left from that absolute timestamp instead of requesting a new event every second. The core omits an expired weekly quota and does not copy a Codex account's quota into another backend's session.

## Transcript rows and cards

An `Entry` contains `id`, `kind`, Markdown/source `text`, `done`, nullable `tool` and nullable `operation`. Kinds are `user`, `reasoning`, `commentary`, `answer`, `tool_call`, `tool` (tool output), `notice`. Optional `format` is `plain` (the default), `user_steer` or `diff`; optional `file_path` names the source file for code/diff rendering. These facts preserve the original role and format even when the body travels separately. A client uses nullable `tool` to recognize tool facts, including a diff whose original role differs from tool output. Clients wrap and style source text for their own width. No row carries a terminal dimension, vector offset, color or key binding.

A tool call/output or diff row carries its compact facts in `tool`; its `text` is empty. The client reads the large body with `entry/output` when needed. Tool facts contain `kind` (`command`, `read`, `search`, `edit`, `other`), `label`, `label_source` (`fallback`, `literal`, `ai`), `status` (`running`, `ok`, `failed`, `interrupted`, `unknown`), nullable `summary`, nullable `added` and `removed` counts, `has_output` and decimal-string `output_revision`. Unknown facts remain unknown. EP018 exposes current labels, paths, diffs, completion and failure facts. EP021 supplies richer tool classifications, success/interruption facts, summaries and diff counts from native data. Clients must not infer success from `done: true` or from a null count. `label_source: fallback` means the core has no saved label and supplies a generic description. A saved literal label can have the same text, so clients must preserve this origin when deriving a compact diff label from original source. Tool calls may have `has_output: false` while still owning source text; that flag describes output, not whether a tool-call body can be read.

Output segment kinds are `plain`, `addition`, `deletion`, `hunk`, `context`, `command`, `success`, `error`. The core currently classifies diffs and otherwise emits plain pieces. A piece can end inside a line; concatenate its text exactly, including newlines. Clients choose colors and wrapping. A tool's fallback label is fixed text, never its growing first output line.

### Bounded running output

`OutputChunk` contains `entry`, `revision`, nullable `from`, `next`, `segments`, `has_more`, `done` and `seq`. Each segment contains `kind` and `text`. The opaque `next` token resumes the body after the supplied `from`. Tokens are entry-bound, ASCII, at most 256 bytes; clients must never construct or edit them. Revisions are decimal strings preserving 64 bits. The core consumes at most 65536 source bytes and emits at most 256 pieces per read. It clamps smaller byte limits to at least four, allowing a complete UTF-8 character. JSON escaping and envelope bytes add bounded overhead.

The token carries a source position and bounded terminal-control and diff-prefix parser state. The core reads only the new suffix of its original body. It stores no second normalized body and never scans an old prefix to resume. A chunk may contain no visible text while advancing through a split or unterminated escape sequence. `has_more` means buffered source remains; `done` means both source and execution have ended. An incomplete final diff prefix waits for another character or completion. A completed cursor that later encounters unexpected appended data requires a fresh read because its final prefix may already have been emitted.

The session stream carries `output_changed` with `entry`, `revision`, `has_output`, never the body. Every session subscriber receives it, including collapsed clients; no sequence number is skipped. A label, path or completion change sends ordinary entry facts and preserves an unchanged body's revision. A replacement changes the revision and sends current entry facts. An expanded client clears its displayed body and restarts without a cursor after a replacement; retired ids fail explicitly. A snapshot supplies current revisions and lets a client retain valid watches across a reset.

An optional `entry/output` notification contains `OutputUpdate`: `session` and `chunk`. Its `seq` stamps the session facts used to read it, but does not advance the session-event cursor. The output cursor advances independently. The client accepts only the expected `from` token for that entry/revision, so delayed or duplicate chunks cannot append twice. A reconnect resumes the session first, checks the current row/revision, then subscribes at its saved output cursor. A replaced, foreign, malformed or retired cursor fails explicitly; it never guesses a new offset. The daemon bounds watches and outgoing bytes per connection, cancels watches on disconnect, and ends an overflowing watch with entry/output/reset rather than silently dropping part of a body. A client can always recover with a fresh bounded read.

EP018a supplies pure core reads; EP019a adds socket watch scheduling, explicit error codes, connection limits and real two-client process tests. A collapsed client needs no output subscription. Opening a running tool is a supported design requirement, including on the future phone app.

Live approval cards are separate from stored transcript rows because the core already owns them separately. A snapshot includes the active card and queued cards in `approvals`. Each card contains `id`, `kind`, `title`, `details`, `choices`, optional `input`, `submitted`, `active` and `default_to_no`. A card id comes from the same opaque allocator as rows. The core exports only display facts and selected input descriptions, never the native routing payload. A client shows choices the card offers; it must not assume every backend offers session-wide approval.

A card's `input.kind` is `fields`, `form`, `browser` or `unsupported`. A fields input carries neutral `fields`: each has a card-local `key`, `title`, `description`, `secret`, `multiple`, `other`, `notes_only`, `required`, `schema` and `options`. Each option separates its typed `value` from its `label` and `description`. Field keys belong to an answer within this card; they cannot address a session or backend callback. A form input carries its JSON `schema`, a browser input its `url`, and an unsupported input a `reason`. The core uses the same native question readers as the terminal, so a phone does not interpret Codex or Claude question messages. A browser card offers `once` for explicit consent; it does not require an empty form answer. `default_to_no` tells clients to keep a negative default and require explicit consent instead of treating Return as an automatic allow. The terminal's unsent form answers, browser consent, focus and confirmation hints stay in ViewState and never enter a snapshot. An accepted submission sets `submitted`; backend withdrawal and successful answers both retire the card. A resolved-card event carries a nullable `decision`: a known accepted choice is explicit, while null means the card closed without a known user decision. Clients must not label a backend withdrawal as an approval. The core does not persist resolved cards as transcript history in EP018; a new snapshot contains only live cards.

## Events and snapshots

The `session/event` notification contains `session`, `seq` and `event`. The `event.kind` selects one of these records:

- `entry_added` carries a complete `entry` in chronological append order.
- `text_appended` carries `entry` (id) and only the new `text`. Text is appended exactly, including Unicode and newlines.
- `entry_updated` carries a complete replacement `entry` with the same id. This event handles edits that cannot be represented by a suffix. All fields replace old values, including nulls and empty text.
- `entry_facts_changed` carries `entry` (id) and `facts` with `kind`, `format`, `file_path`, `done`, `tool` (plain format and absent paths may be omitted). It changes those facts without resending text. It preserves output cursors when `output_revision` stays the same.
- `output_changed` carries `entry`, `revision`, `has_output`; it announces new source without sending bulk text.
- `approval_requested` carries a complete `approval` and nullable `before` card id. Remove that id from the local live-card list, then insert the card before `before`, or at the end when `before` is null. The publisher sends anchors before dependent cards and sends order-only moves. A non-null missing anchor requires a fresh snapshot; do not guess its place. This preserves card order, focus moves and submitted state without exposing a storage offset.
- `approval_resolved` carries `approval` (id) and nullable `decision`. It removes that id from the live cards.
- `tasks_changed` carries optional compact `tasks` facts, without native labels, source bodies or device selection.
- `info_changed` carries complete `info`. It replaces all session header facts. Full objects avoid an ambiguous missing-versus-null patch convention.
- `reset` carries a complete `snapshot`. It replaces a client's stored view at that event's cursor. The snapshot cursor equals the reset event cursor.

A snapshot contains `info`, `entries`, `approvals`, `seq` and `has_older`. Entries form the newest page in chronological order; the default reset includes100 rows. The core read API clamps page sizes to1 through1000. `has_older` includes a private native continuation as well as stored older rows. Every Ready session has adopted a complete initial native window and its source/metadata. Codex requests newest complete100-turn pages; Claude requests the newest complete SDK archive window, normally64 records but expanded when a tool result or assistant block needs an earlier record. The Claude SDK can still import the complete native file before that first archive window is available.

When stored rows cannot fill a checked `session/history` request, the owner reads an earlier native window through its existing bounded worker. The backend cursor, native snapshot, root and connection remain private. A failed or retired read leaves accepted rows intact. The shared client merges the historical prefix at its fixed numbered cursor without overwriting newer live changes or moving another device's view. `prompt/select` can fetch the older matching human or explicitly unknown prompt through that same worker without requiring transcript paging. Repeated windows of one prompt request keep its original source/anchor,20-second deadline and64MiB native-read allowance.

Grok's ACP load replays the complete conversation before Ready. Carlos preserves every supported replayed text/tool row and serves normal client history pages afterward. This backend has no invented native page cursor, and its startup cost remains a full replay. The terminal uses the same shared client and bounded source reads as other consumers; it has no direct native-history reader.

Omitting `since`, supplying a cursor beyond the current clock, or requesting events older than the replay ring produces a snapshot. A client applies events only to the named session. The next cursor must equal the previous cursor plus one. It must not advance past an unknown event kind or a gap; it needs a replay or snapshot. It may ignore updates for older rows it has not loaded. Later history reads include current row facts and a cursor; the shared client in EP019b must merge a page at that cursor without overwriting newer events. An empty replay can confirm the current cursor. Replaying a reset replaces old pages and entry addresses as its snapshot directs.

The core coalesces writes before each `publish` call. New rows carry their final unpublished text once; several suffix writes on an existing row become one suffix. A later replacement supersedes earlier pending suffixes for that row. A completion or label change arrives even without new text. The event numbers order published facts, not every intermediate byte received from a backend. A caller must encode the batch before its next write; Rust enforces this through the batch's borrow of SessionState.

The core holds at most 256 distinct pending row edits and bounds each emitted record batch. Large bursts, history changes and overflow produce a reset instead of an unbounded log. A reset may carry a stable earliest changed id to the in-process terminal as a cache hint; that hint does not appear on the wire. The terminal reads the numbered record, resolves its id and invalidates the same suffix of its render cache. The core does not clone or serialize the whole transcript for each terminal redraw.

The daemon retains encoded events in a bounded replay ring and bounds each client's outgoing queue. A slow client must not stall the session owner; the server replaces a dropped queue with a snapshot. The current borrowed batches deliberately contain no replay promise after a caller drops them. If a local caller drops a batch, the terminal detects its cursor gap and rebuilds from current core facts.

`sessions/changed` carries `kind: "updated"` with complete `info`, or `kind: "removed"` with `session`. The session manager emits those notifications.

The daemon also sends `session/snapshot {snapshot}` when a live subscriber loses its retained event prefix or queued deltas. This replacement uses the snapshot's actual sequence and invents no reset event. An `entry/output/reset {session,entry,message}` ends a lost watch; the client explicitly starts a fresh read/watch. If a shared page exceeds the wire limit, `session/syncFailed {session,error}` ends that session interest while the native owner and private operation results remain alive. Each connection's new subscription/watch generation rejects older in-flight reads.

An initial subscription may expose explicit starting/restoring facts and startup approvals. The owner publishes its history replacement after adoption; a client must observe Ready before treating startup as complete. A new daemon instance or fresh client identity always receives a snapshot. A current-instance authenticated reconnect can resume an event cursor. See docs/daemon-protocol.md for the local-only greeting and the distinction between reconnect and restart.

## Compatibility and proof

Readers may ignore unknown object fields; unknown methods, event kinds, enum variants, invalid ids and unsupported versions fail explicitly. While version 1 is provisional, update types, fixtures, handlers and documentation together. Once the first real remote consumer establishes the contract, required-field or meaning changes need a new version or explicit capability checks. Never make a client silently skip an unknown state change.

Run `cargo test -p carlos-proto` for envelope, version, id and cursor checks. Core event tests serialize real published events to JSON, apply them to a headless client's copy, and compare it with a snapshot after Unicode streaming, normalized reasoning, completion, labels, approvals and history replacement. Terminal checks drive the actual executable against deterministic peers. `.agents/reports/exec018-final-report.md` records the accepted source and measured results once this step is complete.

## Native root goals

Codex snapshots include optional `goal` facts. A `goal_changed` event replaces them in the numbered session stream; null removes the capability. Facts include an opaque `revision`, `knowledge` (unknown/known/unavailable), nullable accepted `goal`, `reading`, `pending`, nullable `direct_input`, `read_error` and `notice`. The accepted value contains objective/status, nullable token budget, tokens/time used and created/updated timestamps. Counters and budgets use lossless decimal strings. Unknown future statuses remain readable but cannot be submitted by accident. Mutation failures belong only to the submitting operation; snapshots never contain another client’s goal editor or mutation error.

`goal/read {session,refresh:false}` returns `{session,seq,goal}` from the current owner. With refresh true it schedules the existing native asynchronous read, without waiting for its reply. The numbered stream carries subsequent states. A client accepts a read only if it does not predate the most recent goal event or full session snapshot. Unrelated newer transcript text does not invalidate a safe goal read.

`goal/subscribe {session}` starts a connection's explicit goal read interest and returns the same snapshot shape as `goal/read` with a fresh native read scheduled. The connection must already subscribe to the session. The daemon combines all current readers and uses the existing thirty-second native goal timer while any remain. `goal/unsubscribe {session}`, session detach, and socket disconnect each release only that connection's interest. The last reader stops periodic refresh; native startup and explicit reads still establish facts needed for Ralph safety. A reconnect restores the shared Client's wanted goal reads after its session facts return. Closing the panel while offline cancels that restore.

`goal/set {session,operation,expected,change}` changes only the root goal. `expected` is the current opaque revision, scoped to the logical session, native root/connection and accepted goal state. `change` contains an explicit native status (active/paused/blocked/usageLimited/budgetLimited/complete), optional objective and optional positive signed-64-bit token budget. Missing objective/budget retain native values; a new goal requires an objective up to 32 KiB. Missing status is rejected, rather than defaulting to active. `goal/clear {session,operation,expected}` explicitly clears a goal; clients do not remove budgets or reset counters through a sentinel value. Both commands use the normal ordered lane and private retry results. Native acknowledgements confirm admission, never execution or completion.

The owner rejects stale revisions, unsupported/unknown controls and a pending goal mutation before native I/O. Starting/resuming an active goal also requires Ralph and any pending Ralph toggle to be off. Ordinary chat and task reads never create or resume goals. Typed commands expose no native thread id, method name, origin or raw native parameters. The native adapter retains its original request token/epoch/deadline; captured permissions are checked at writer dispatch. Closing a connection or switching roots makes unfinished results uncertain and retires queued native writes. A late reply cannot update the new root. Equal read responses retain a draft’s revision; even an equal unsolicited native event still fences a racing activation acknowledgement.

## Native queue reads and changes

`Snapshot.queue` and numbered `queue_changed {queue}` events contain optional QueueFacts for native Codex queues. Facts contain an opaque QueueRevision, known/reading/pending flags, the last accepted entry count, a bounded read diagnostic and a native acknowledgement notice. They contain no selection, editor or mutation failure. The core retains native inputs under its existing whole-read limits of 4096 entries, sixteen MiB and twenty seconds.

`queue/read {session, expected?, after?, limit?, refresh?}` returns QueuePage with session, seq, queue facts, at most 32 entries and has_more. Omit expected/after to begin; use the returned revision and last entry id to continue. The daemon keeps no per-client queue selection or paging window. A changed/unknown revision rejects a continuation. An unknown queue returns no entries until the native read completes. Explicit refresh cannot also continue a page; it retires previous queue preconditions and starts a new native read. Count can describe the last accepted queue while known is false.

QueueEntry contains an opaque root/connection-bound id, a bounded client-message label, a preview of at most 1024 characters, preview_complete, and nullable text_bytes. The native entry id and raw input object remain private to the adapter. text_bytes is present only when the entire native input is one plain text item with no rich spans or unknown fields. `queue/text {session,expected,entry,offset,limit?}` returns at most 64 KiB of that exact text with revision, entry, offset, next_offset and complete. Byte positions are decimal strings; a seek inside a UTF-8 character rounds down at most three bytes. Attachments and rich input stay intact and cannot be read as editable plain text.

A client merges a page header only after that session reaches the page's sequence, and refuses any header older than its latest numbered queue fact. The terminal retains one preview page, follows opaque page cursors, and reads a selected editable input completely before exposing its local editor. It keeps the edit revision fixed when other clients move or delete entries.

`queue/change {session,operation,expected,change}` admits a private operation. Change.kind is add (text), edit (entry,text), delete (entry), start (entry), or move (entry,direction up/down). Every change checks current known queue facts; no client can provide native methods, backend ids or arbitrary input JSON. New/edited text must be nonempty and at most 512 KiB; escaped native requests also fit the existing writer budget. Move swaps the selected entry with its adjacent entry using the complete accepted native order. Start/delete/move preserve attachments; edit rejects any input Carlos cannot reproduce exactly.

The owner keeps queue changes in its bounded ordinary mailbox. A queue change at the front can reach the existing guarded native writer while a chat prompt waits for a reply. A pending fork or rename remains a barrier, and approvals and interrupts retain their separate control lane. The owner retains native request tokens and writer permissions until the exact acknowledgement. A held queue write does not block ordinary chat, reads, interrupts or approvals. Native acceptance reaches only the originating ClientOperation, with exact submitted text on rejection/uncertainty and no automatic replay. Repeated identical operations return the retained result instead of adding another message. Rewind keeps its existing safety rule: an unconfirmed queue write blocks the thread switch and preserves the edited prompt. Native closure makes unconfirmed queue work uncertain and retains its submitted text privately.

## Shared Rust client

`crates/carlos-client` now supplies a pure `Client`. It owns checked copies of session facts, private operation results, bounded body windows and metadata for pending requests. It depends only on the protocol crate, serde and serde_json. The platform owns sockets, clocks, input widgets, rendering and any writer queue.

The platform calls `Client::begin`, writes the returned Outbound bytes, tags incoming frames with that Outbound's connection id and passes decoded envelopes to `Client::receive`. Effects contain changed session/operation/body ids, correlated panel reads, errors and more outgoing reads. The platform writes those requests in order. `Client::submit` assigns a private operation to an explicit user command and retains its original text before handing bytes to the writer. A failed or possibly partial write keeps the exact text; reconnect queries retained outcomes and never resends a mutation. An older socket cannot change the replacement connection's facts.

A retained Ready copy does not authorize new session work after reconnect. `session_is_ready` requires the matching subscription reply to succeed on the current greeted connection. A failed or superseded reply keeps drafts and cached facts but leaves new sends, queue changes and queue reads blocked until an explicit successful subscription.

The client requests one complete snapshot after a sequence gap. It rejects superseded subscription replies, binds authoritative prompt rows to their operation and prevents a late pending reply from undoing acceptance. Each catalogue stays below 4096 sessions/four MiB. At most 32 session windows share a 64-MiB retained-fact allowance. These counters include source/label strings, encoded cards and fixed metadata allowances; they are not exact heap/RSS figures. If a window exceeds that combined allowance, the client detaches that window, reports the reason and retains other windows, private submitted text and native work.

A history read can arrive before the numbered stream reaches its sequence. The client holds at most 32 such pages under a combined eight-MiB data allowance. It applies a held page when that fixed cursor arrives, preserving newer known rows and rejecting changed unseen rows or moved anchors. It never waits for a continuously running backend to become idle. Pending request metadata is limited to 128 requests/four MiB of encoded request charges; private submitted/recovery text remains under its separate 128-operation/four-MiB allowance.

The platform opens original-source or normalized-output windows through `Client::bodies_mut`, then uses `read_body` or `watch_body` with the returned local token. At most 32 windows share eight MiB of retained body data. Default source and normalized windows keep 256-KiB suffixes with bounded piece counts. A platform can instead request `open_source_document` to retain original bytes in one contiguous string under the same aggregate allowance; `SourceWindow::document` lends it only when the entire observed body is present. This cache allowance does not define an accepted product body limit. Local capacity failures preserve direct-read cursors for an explicit retry after unused windows close; a failed watch stops only that read and never resubscribes itself or discards private submitted text. Windows expose discarded prefixes; revisiting original bytes uses a checked direct seek. Original text keeps split controls and Unicode exactly. Normalized pieces keep their separate line kinds and cursor. Neither view reconstructs original bytes from stripped display text.

The client activates a body watch after its first reply. An older reset closes only that older local token while a replacement waits for its own reply. Closing a pending watch queues an unsubscribe and prevents a late reply from reviving the window. Source and normalized watches remain independent. When shared facts replace a body, the client cancels the old watch before requesting the new generation. A live reconnect restores session facts before resuming a body cursor; a daemon replacement retires old body rights. `close_body` returns Effects whose outgoing cancellations must be written by the platform.

These Rust interfaces do not complete the terminal cutover. The terminal still needs concrete source/layout/color/copy consumers, the remaining typed native controls and socket-backed workflow parity before its embedded backend/session path can be deleted.


## Native task metadata reads

`task/list {session,expected?,after?,limit?,refresh?}` returns a TaskPage with session, seq, an opaque TaskRevision, known/reading/closed flags, at most 32 compact tasks, has_more, native_older_available and a bounded read error. Omit expected/after for the current first page. To continue, supply its revision and last TaskId. Several clients can read different pages without changing a shared selection. A changed native view rejects an old continuation. Explicit refresh cannot continue an old page. For Codex, it starts the existing bounded descendant/process reader; ordinary task/list calls do not start it again while the accepted window remains known. Claude reads already received native task facts. Grok returns an explicit unsupported error.

TaskId includes the logical session, native root, backend and connection generations. Codex exports only records with current verified ancestry or root-owned processes. TaskKind distinguishes agent, process and task. Labels advertise label_complete and their full text is available through the named label field. Labels and native state names remain bounded; an unknown native state stays readable. An optional opaque TaskRun names the observed child turn, Claude run or process item/PID. Missing run evidence stays absent. The typed Client supports these reads and private task stops. Child activity/history and independent older native windows remain unfinished EP019b checkpoints.

`task/detail {session,expected,task}` returns the same task address and typed TaskProperty previews. TaskField admits only named scalar fields such as role, report, command, directory, usage and description. Existing panel labels also use native_id, owner, last_turn, process_item, run_label, can_stop and native_state; these are display text, never trusted routing inputs. The server does not accept native JSON paths or return arbitrary native objects. Each preview contains at most two KiB plus the full byte length and a complete flag. `task/text {session,expected,task,field,offset,limit?}` reads an exact field in chunks up to 64 KiB. Decimal byte offsets remain lossless and a seek inside a Unicode character rounds down at most three bytes. A changed view or foreign task rejects both metadata and text reads. All three reply types fit the existing half-MiB read reservation; native metadata keeps its original core bounds.


`task/run {session,task,read?,refresh?}` returns TaskRunSnapshot with the opaque task address, nullable read id/run token/native state, known/reading/closed flags and a bounded read error. An attached Codex agent can be active without an observed turn id. This command uses the existing native turns/list request with itemsView notLoaded and limit one; it never resumes or stops a child. Several tasks retain separate tokens and original twenty-second deadlines under an eight-read cap. Only ids/status and a metadata fingerprint remain cached; native turn items are discarded. A completed empty read is known with no run, which differs from missing or evicted evidence.

Start without read, using refresh for an explicit new current-run request. If the reply is still reading, poll with its exact read id and refresh false. A replacement/eviction rejects an older read id instead of letting its caller follow another client's newer run. A changed original task/root/connection produces an explicit error; it cannot turn the old intent into a stop for a replacement turn. A fresh accepted native result takes precedence over older observed metadata, including an explicit empty result. Cached run tokens and the bounded run-read availability stamp participate in TaskRevision. A pending/read-complete transition advances that revision even when the returned turn id/status equal cached metadata, so a waiting stop intent can continue through numbered facts without a terminal polling clock. Claude and native process rows return their already observed run evidence without native I/O. This command reads identity only. `task/stop {session,operation,task,expected_run}` uses the original root, generation and exact run/PID/item fences at native dispatch. Its private result confirms native admission rather than task completion, and an uncertain write never authorizes an automatic retry.


### Compact task facts and explicit list interests

`Snapshot.tasks` and numbered `tasks_changed {tasks}` events contain optional TaskFacts. They contain separate opaque metadata and overview revisions, known/reading/closed flags, counts for agents/processes/tasks/active work, native_older_available, a bounded read diagnostic and a notice. Every session subscriber receives these compact changes, including clients without native polling interest. Root transcript deltas do not rescan retained native task bodies. Private task pages and detail text never replace the accepted compact facts.

`task/subscribe {session}` requires an accepted session subscription, starts that connection's explicit list interest and returns `{session,seq,tasks}`. The daemon combines readers across connections before running the existing three-second Codex native list refresh. `task/unsubscribe`, session detach and disconnect release only that connection's reader; the last release stops periodic list refresh. These operations never send chat or stop a native task. The shared Client restores wanted readers only after the session subscription succeeds on the current greeted connection. Closing while offline cancels that restore. A failed old subscription cannot release a newer one.

`Client::merge_tasks` checks the session sequence against the most recent accepted task fact or snapshot and the current numbered stream. A stale or future reply cannot overwrite current facts. `Client::check_task_page` checks a bounded device-owned page against that same accepted metadata revision and flags. A future read waits for the normal numbered stream; the task path adds no general reply queue.

### Read-only task overview

`task/overview {session,expected?,after?,limit?}` returns `{session,seq,revision,entries,has_more}` with at most 32 rows. Omit expected/after for the first page; continue with its overview revision and final opaque TaskOverviewId. The row kinds are main (Claude activity, optional thinking token count and transient label), quota (label, finite used percentage and absolute reset timestamp), prompt (accepted native prompt label, consumed flag and steer/queue priority), and process_error (verified Codex owner label and diagnostic). Accepted prompt source, native task bodies, settings and callback answers are absent.

Each overview label contains at most two KiB, full decimal-string byte length and complete. `task/overview/text {session,expected,entry,field,offset,limit?}` reads only label or message from the addressed row, up to 64 KiB with exact offsets and completion. The client rejects foreign or stale identities, repeated page rows, oversized previews, invalid percentages and malformed UTF-8 ranges. A device computes reset countdowns and hides expired quota windows locally.

The daemon schedules Claude's existing optional quota read at its five-minute deadline through bounded native action workers. The embedded wrapper uses the same prepare/reply rules. A full worker backlog skips only that optional read until its next deadline; it cannot stop the session or create a busy retry loop. The native adapter preserves the original read number, root/helper scope and stream revision. A late report cannot overwrite a replacement root or newer native stream facts. This overview adds no settings command or terminal polling clock.

## Local device controls

The operator provisions each device through the private Unix socket:

    carlosd device add --socket PATH --name 'My phone' --token-file NEW_PATH
    carlosd device list --socket PATH
    carlosd device revoke DEVICE_ID --socket PATH

The add command creates a new mode-0600 file and refuses existing files or symlinks. It writes and syncs the file and its directory entry before requesting a grant. The file contains one line: a 32-character lowercase hexadecimal device id, a dot and a 64-character lowercase hexadecimal secret. The command draws the secret's 32 bytes from OS randomness. The catalogue stores only the device id, a single-line name of at most 256 UTF-8 bytes and the secret's BLAKE3 hash. The command prints the public id and file path; it never prints the secret. A failed or uncertain grant keeps that file and never automatically issues another credential.

These typed methods require a greeted Unix peer with matching OS credentials:

- `device/add {operation,device:{id,name},verifier}` provisions one verifier or its exact duplicate. A different verifier or name under an existing id is rejected. The verifier contains 64 lowercase hexadecimal characters, encoding BLAKE3 of the raw 32 secret bytes.
- `device/list {}` returns `{devices:[{id,name}]}` for currently allowed grants. It returns neither hashes nor secrets. A device blocked by an unfinished or failed revoke is omitted.
- `device/revoke {operation,device}` blocks that device's access and retires its private retry leases. It reports accepted only after the catalogue durably deletes the grant. A disk failure reports uncertain and keeps the device blocked for this daemon lifetime; a restart may reload the unchanged durable grant. Fix the disk and submit a new explicit revoke to finish it.

Add/revoke return the existing private OperationResult without a session address. They reserve their own bounded result and ingress space, so full ordinary/native-control queues cannot consume the operator's allowance. An old add retry returns its retained result and cannot undo a later revoke. The operator CLI greets and submits exactly one action, without opening a native conversation, including when all 16 owner slots are full.

A network client supplies the file's token line in hello's `token`, independently of its private `resume_token`. `Client::begin_with_token` constructs that greeting while the platform owns token storage and socket I/O. AccessToken and ResumeToken hide their bytes in Debug output. Retry leases distinguish Unix callers from each authenticated DeviceId; another device cannot borrow even a correct private resume credential. The listener stays off until the operator supplies `--listen IP:PORT`.

## Optional WebSocket listener

Start `carlosd --socket PATH --state-dir PRIVATE_DIRECTORY --listen 127.0.0.1:PORT`
for loopback, or choose the host's specific WireGuard address. Plain WebSocket
traffic needs that private encrypted network when crossing machines. A native
client may omit Origin. A browser needs `--allow-origin` with its exact Origin;
other origins, query strings and requested subprotocols are rejected at upgrade.
The server never negotiates compression or accepts a token through the URL.

Send the same typed JSON-RPC envelopes as text messages. The first `hello`
contains the device token; initial input is limited to four KiB and must finish
within five seconds of TCP acceptance, including the HTTP upgrade. After a
successful greeting, each incoming aggregate message may contain at most four
MiB; outgoing messages may contain at most eight MiB. Binary messages and
malformed UTF-8 fail without dispatch. Ping/pong and close use WebSocket control
frames. The daemon closes WebSocket writes after 500 ms without successful TCP write
progress. A large frame may take longer while the reader keeps draining it; its
outbox bytes stay charged until flush. The daemon retains the private
operation results for an authenticated reconnect.

The daemon allows 16 network sockets separately from 16 local sockets, with at
most four unfinished upgrades/logins. A saturated network listener cannot take
the Unix operator's connection or device-control allowance. Revocation closes
only that device's sockets and retry leases; already admitted native work and
other clients continue.
