# EP019b: save Codex choices through the daemon

The daemon now accepts typed `settings/set` requests for Codex. Each request names the session, its private operation, the exact settings revision the editor read, and the fields the user chose. An omitted field stays untouched. Core rejects stale revisions and invalid advertised choices before native writes. The endpoint does not expose arbitrary native method names or accept an editor's internal indexes.

Core reuses the existing future-turn and live-turn settings code. Each pending change keeps its original native request token and a permission flag checked by the native writer. Closing or replacing that request revokes its queued writes. A reply must match the original root, epoch, token, method and submitted values. Future-turn and live-turn replies settle separately; the private result describes partial success rather than claiming that an already running model request changed.

The daemon waits for this change before dispatching later ordinary commands. Its independent read and control lanes still answer session reads, approvals and interrupts. Reconnecting the requesting client retrieves its private result without resending the native change. Duplicate operations return the same retained result.

The daemon captures the requested defaults before native I/O. Only a confirmed future choice, or the existing precise unsupported-API fallback, permits an optional default-file write. The existing ordinary worker writes the complete captured values through `runtime_preferences::save`. A newer native notice cannot substitute another client's choices into that file. A disk error returns native success with an explicit save-failure notice. Rejection, malformed acknowledgement and connection loss do not write defaults or trigger an automatic retry.

Startup tests found that an older native metadata read could arrive after a settings request and make its acknowledgement appear stale. The dispatcher now retires that older read, and the shared metadata reader waits for pending settings to settle before starting a fresh read. Metadata from a legacy server cannot erase Carlos's explicit next-turn fallback. Core adds no new scheduler, read counter, cache allowance or settings database.
