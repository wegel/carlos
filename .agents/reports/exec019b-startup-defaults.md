# EP019b: apply saved defaults when the daemon starts a session

Commit `dd367c8` lets the daemon read the existing runtime-defaults file on its bounded launch worker. The session owner and socket manager do not wait on that file. The embedded launcher and daemon now call the same pure model/effort resolver and fallback-catalog helper, so the migration does not maintain two copies of those rules.

For a new Codex session, the daemon waits for the complete native snapshot and catalog before choosing compatible defaults. It leaves accepted native facts separate from requested differences and sends only those differences through the existing settings sender. The initial marker runs once; a later reconnect does not reapply startup defaults. Resumed Codex sessions retain native choices, including unknown values, except for the existing explicit reasoning-summary environment override. Claude and Grok retain their existing saved-preference and native-capability rules for create and resume.

The first candidate exposed an older metadata read that superseded the startup acknowledgement. The settings foundation fixed that shared reader rather than adding a second startup control path. A later fixture cleanup failed while copying a FIFO into artifacts; the fixture now closes and replaces that temporary FIFO before cleanup. These rejected runs remain recorded and are not passing evidence.

The final candidate passes seven actual-daemon startup workflows and both existing settings-facts workflows. The tests cover saved values, unsupported effort, models without effort, new-session summary defaults, native resume and environment overrides, the empty-catalog fallback, and Claude/Grok prompts before and after restore. A real blocked defaults-file read leaves the manager and an already running session responsive. The same saved-choice test fails against the pre-change daemon because that daemon ignores the file.
