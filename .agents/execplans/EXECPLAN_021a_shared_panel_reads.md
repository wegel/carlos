## Purpose / Big Picture


A phone or web UI should be able to open settings, a goal, the native prompt queue and native task panels by passing messages through carlos-client once. Today the terminal contains the rules that join pages, wait for matching numbered facts, reject stale replies and fetch long fields. Another client would have to copy those rules. Move that work into the shared Rust client and delete the terminal copies, while keeping the terminal's keys, layout, selected row and editor drafts local.

The terminal must keep the same visible behavior. A small test-side Rust consumer must also read complete supported panels through an actual daemon without importing terminal controllers. This is the observable proof that the phone can reuse the work. The native backends and wire protocol remain the same unless a concrete correctness issue requires a small documented change.

EP021 is split at a natural boundary. This plan shares existing read behavior and completes the small EP020 follow-ups. EP021b will add paged native history, Grok approvals and richer tool data after these common readers exist. EP022 still builds UniFFI bindings and the actual Swift iPhone app, then measures that consumer on the remote Mac. Do not add speculative phone commands, a generic panel framework or a second native owner here.

## Surprises & Discoveries

The first terminal run after the list/window adapter passed28/29 cases. Its one failure asserted a task/window/close with window:null, the old broad close-all implementation. The retained RPC trace shows an exact close for the owned ab723911e6fdf9c424abe222f8f3556aa21707dd9964268011f0104e9b66fd40 window, while the screen and composer remained correct. Update that held-window check to capture the original read's window id and require exactly one matching close. Do not restore broad close-all or relax the deadline. The full29-case rerun passes.

The daemon already holds TaskWindowRead until a captured native read stops reading (crates/carlos-core/src/engine/task_windows.rs::defer_task_window_read), so the shared reader can request the next header without a polling clock or a rapid immediate-reply loop. TaskSubscribe also installs its native interest at admission and finish_task_subscription checks that original generation instead of reinstalling a canceled interest. Its owned closing acknowledgement can retire through the existing ordered unsubscribe path. Allocating TaskWindowOpen requests retain their ids until an exact native window can close; explicit unowned window reads remain untouched.

A same-value TasksChanged event advances Replica.task_sequence without setting ChangeSet.tasks. A failed task page and field must wake on that numbered task sequence, while an unrelated root text event must not retire the failure. The new pure workflows cover both; the detail reader now sets its dirty flag when its scoped failure clears. Count sums use u64 before checking4352, so even three u32::MAX counters cannot overflow into a partial task view.

An activity open can allocate a native reader before its reply arrives. A common reader cannot blindly forget that point id on close or send a broad close-all that also closes explicit unowned readers on the same socket. TaskActivityPanel retains only those allocating ids in the existing128-request tracker, consumes their late replies and closes each exact returned native id. Known readers close by exact id before a replacement opens. EOF drops all old rights and never automatically opens the retained child on the replacement socket. A closed-native header still has an exact interest to release; user-visible stale state and socket-owned rights therefore must not be conflated.

The captured older-window long-field bug now has an actual failing-before/passing-after terminal proof. The old text assembler compared a captured-window reply with the latest task header, repeatedly requested its same offset and never displayed the command's final marker. TaskDetails instead retains its original window/revision/task through all named reads. Latest-window reads still reject changed latest headers; captured-window reads never merge their data into the latest facts. A disconnected captured reader keeps readonly fields and never automatically sends its expired window on a new socket.

The existing terminal accept_task_text checks text.revision against latest task_facts even when its request used a captured older task window. Code inspection indicates that valid older-window continuation chunks can be discarded repeatedly while the property remains incomplete. Add a real long-field/captured-window regression during the details-reader move and use the original window/revision/task target; a passing short older-task fixture does not cover this path. Keep terminal report/label display choices outside the reusable reader.

The daemon registers a goal watch when queue_read admits it and removes that interest immediately on GoalUnsubscribe; read completion does not register it again (crates/carlosd/src/manager/goals.rs). Therefore an owned GoalPanel can retire its pending reply id when it uses the existing ordered close_goal path. Keep this cancellation scoped to that owned panel, not a generic cancellation of every watch acknowledgement. The pure close-before-reply case and actual last-reader workflow both pass.

Task detail code currently treats the agent report limit of65536 bytes as a terminal display choice, while other selected fields allow the existing eight MiB native view. ## Context and Orientation


The daemon owns one mutable native session in carlos-core and accepts Unix or authenticated WebSocket clients through one manager. carlos-proto holds the typed wire data. carlos-client is a pure state machine: platforms own sockets, clocks and rendering and pass each incoming message to Client.
